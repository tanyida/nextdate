# Next Date: MVP prototype

A mobile-first web app that turns a couple's preferences into a Singapore date plan (an activity, a meal nearby and a shareable invitation), built from the Next Date PRD.

It has **no build step and no dependencies**: plain HTML, CSS and JavaScript. You can host it on any static host (Vercel, Netlify, GitHub Pages, S3), or run it locally.

## Run locally (Windows, nothing to install)

```powershell
powershell -ExecutionPolicy Bypass -File serve.ps1 -Port 8080
```

Then open http://localhost:8080/. The editor console is at http://localhost:8080/admin.html.

Any static server works too (`npx serve`, `python -m http.server`). Opening `index.html` straight from disk also works, but the service worker and cross-device share links need http(s).

## What's in it

| Screen | Where | Notes |
|---|---|---|
| 1. Preferences | `#/` | One scrolling screen of chips. Everything except category has a default. Optional extras sit in "Meal, vibe & more". There's also a 🎲 Surprise me button. |
| 2. Recommendations | `#/results` | 6–10 ranked cards with events first under "Happening on …". Each card has a meal pairing (swap ↻), rain backup, expert tip, source credit and a report link. Actions: add to plan, save ♡, done it ✓, shuffle. A sticky plan tray (max 3 items) shows time and cost. The empty state suggests which filter to relax. |
| 3. Invitation | `#/invite` | 5 templates with a live preview. Fields: partner and sender first names, a suggested opening line, a message, a cost toggle and an expert conversation starter. Share via WhatsApp, Telegram, copy link, native share, PNG image, PDF (print) and `.ics`. |
| Partner RSVP | `#/i/<token>` | "I'm in" / "Another time" / "Something else" with an optional note. The partner replies to the sender over WhatsApp or Telegram with a response link. |
| RSVP receipt | `#/r/<token>` | The sender opens the response link and the plan's status updates in My plans. |
| My plans | `#/plans` | Sent invites with RSVP status, saved ideas, and the "we've done this" list (with undo). Works offline. |
| Editor console | `admin.html` | Listings review (approve, hide, pin, verify, edit, publish blockers, OneMap geocode), pasted-listing import and validation, the expert tip library (≤ 30 words enforced), restaurants, funnel metrics, expiry job, and JSON export/import. |

## Navigation

The top menu is **Plan a date · Latest events · Gift ideas · Memories · My plans**: plain text links, with the current page in bold. On phones it becomes a row that scrolls sideways under the logo.

## Latest events, Gift ideas and Memory book

**Latest events (`#/events`)** is a month calendar of upcoming events. It only appears **after the user has stated their preferences** on "Plan a date", and uses exactly those preferences (date type, budget, region, time of day, kids); it has no separate filters.
- **Before preferences:** the page asks the user to set them first, then returns them to the calendar.
- **On the results page:** after "Find dates", the same calendar is the **📅 Latest events** tab, next to **💡 Date ideas**.
- **Navigating:** the calendar opens on the chosen date. An "All events" switch shows everything that's on.
- **Each event** has **Plan a date →**, which goes straight to the invitation using the event's date and time, plus a Details & tickets link and ♡ to save.

**Gift ideas (`#/gifts`)** lists 26 ideas, data in `js/gifts-data.js`:
- **Shop gifts:** well-known Singapore brands, e.g. Far East Flora, TWG Tea, Bacha Coffee, Bengawan Solo, RISIS, Bynd Artisan, Beyond the Vines and Supermama. Each links to the brand's official site.
- **Experience gifts:** these turn straight into a date plan (pottery, couples' massage, cooking class, Night Safari).
- **DIY ideas:** "Open when…" letters, a printed memory book, re-creating your first date.
- **Filters:** occasion, budget, gift type and **love language**. Each idea has a "Why it works" note from a relationship-expert angle.
- **Saving:** saved gifts appear in My plans.
- **Disclosure:** brands are listed unpaid, with a `sponsored` flag ready for future paid placements. Photos are illustrative (Wikimedia), not brand product shots. Editors should verify each listing before launch.

**Eventbrite ingestion (`ingest-eventbrite.ps1`):**

```powershell
powershell -ExecutionPolicy Bypass -File ingest-eventbrite.ps1 -Pages 5 -DelaySeconds 3
```

- **Source:** it reads the public "this weekend" listing pages at `eventbrite.sg/d/singapore/events--this-weekend/`. Eventbrite's robots.txt allows these pages for general crawlers. Requests are spaced by `-DelaySeconds`.
- **What it keeps:** facts only (name, dates, start/end time, venue, address, coordinates, category and the event link). Each event gets **our own one-line description**.
- **What it never stores:** Eventbrite's descriptions or images. Cards link to Eventbrite for photos and ticket prices.
- **Validation:** listings with past dates, a location outside Singapore, or no link are dropped. Online, cancelled and non-date listings (training courses, seminars, networking, religion talks) are skipped.
- **Output:** writes `js/events-eventbrite.js`. The events show in the calendar **and** in recommendations (as "Happening now"), with "Price on Eventbrite" and "+ tickets" in cost estimates, since the listing pages don't include prices.
- **Refreshing:** run it again to refresh. In production, run it on a schedule (e.g. daily) and send new events through editor review. Here they go live immediately but are tagged `auto_imported`, and editors can hide them in the console.
- **Permission:** confirm content permission with Eventbrite before launch, as the PRD requires for every source.

**Memory book (`#/memories`):**
- After a date, add up to 12 photos (resized on the device to at most 1600 px), a mood, and four guided reflections: favourite moment, something I appreciated about you, what made us laugh, and next time let's…
- My plans shows a "📸 Add memory" button on past dates, and the Memory book shows a nudge for dates with no memory yet.
- Memories can be edited, deleted, shared (Web Share, with photos where supported) or exported as one self-contained **keepsake HTML file** with all photos embedded.
- Everything is stored **only on this device** (IndexedDB) and works offline. Syncing between partners would need sign-in (PRD FR-14/FR-20).

## Booking links, meal choices and photos

- **Activities that need booking** show a "Book tickets" link to the listing's `booking_url`, or to its official page if there isn't one.
- **Restaurants that need a reservation** show "Reservation recommended" with a link. Reservations are flagged for all $$$/$$$$ places plus a curated list. The link goes to the restaurant's `booking_url`, or to a Google Maps search (most listings there have "Reserve a table").
- **Booking reminders:** the invitation builder lists every booking and reservation to make before sending, and the invitation itself carries the same links.
- **Meal options:** every card offers **at least 3 lunch or dinner options** to pick from. The search starts within 1.5 km and widens to 2.5 km, then 4 km (6 km when a dietary filter is on). A card says so when fewer spots match a dietary need.
- **Photos:** every activity and restaurant has a photo, loaded lazily from **Wikipedia / Wikimedia Commons** (freely licensed), with a credit link in the full-screen viewer.
  - Places with their own article show the venue itself.
  - Otherwise the photo is labelled **"Typical dish"** or **"Illustrative"**, so nobody mistakes it for that exact place.
  - Editors can set `image_url` to their own licensed photo instead.

## How the PRD's recommendation rules are implemented (`js/engine.js`)

- **Hard filters**: listing is live; event date range covers the chosen day, including weekday-only runs; time slot; couple cost ≤ budget (kids counted at half price); duration; kid-friendly with minimum age; indoor/outdoor; region (strict when it has ≥ 6 ideas, otherwise topped up from adjacent regions, which are labelled).
- **Score (0–100)**: category 30 (partial for related), region 20 (partial for adjacent), timeliness 20 (events above evergreen, higher if ending ≤ 3 days), vibe 15, novelty 10 (saved and repeat views penalised; "done" items are hidden), editorial pin 5.
- **Diversity**: at most 2 per primary category in the top 6, and at least 1 evergreen in every list.
- **Meal pairing**: within 1.5 km (widened to 3.5 km if nothing's nearby); open across the PRD meal windows (lunch 11:30–14:30, dinner 18:00–21:30); dietary needs are a hard match; cuisine is preferred; restaurants fit the remaining budget.
- **Expiry**: events past their end date are filtered at query time, so they never show even if the expiry job hasn't run.

## Important: what is placeholder

- **All content is illustrative demo data.** Venues are real public places, but prices, hours, the "event" listings and their dates are placeholders written for this prototype. Editors must verify or replace every entry before launch. No source text or images are reproduced.
- **Expert tips** are placeholders pending the confirmed relationship expert and their tone guide.
- **Opening lines** come from a rule-based list. An LLM could write them server-side later, with output reviewed against the tone guide. It should never invent venues.

## Prototype vs production

This build is local-first so it runs anywhere with zero setup. Here's what that means and what changes for production:

| Area | Prototype | Production (per PRD stack) |
|---|---|---|
| Content & admin | Seed file plus editor changes saved in the editor's browser; JSON export | PostgreSQL/PostGIS (e.g. Supabase); console behind real auth and roles |
| Admin access | Unprotected page (`noindex`) | **Must** sit behind sign-in before launch |
| Invitation links | Plan data compressed into the URL fragment, which servers never see. Unguessable, carries no surname or phone, and expires 30 days after the date | Short slugs in an `Invitation` table, with server-side expiry and RSVP |
| RSVP notification | Partner replies via WhatsApp/Telegram with a response link | Server stores the RSVP and notifies the sender |
| Ingestion | Editors paste listing text, then extract, validate and draft | Scheduled weekly fetcher (permission first, respecting robots.txt) feeding the same extract/validate code; daily broken-link check |
| Analytics | Local counters per browser, shown in the console | Cookieless self-hosted analytics with the same event names |
| Weather | Rain backup always offered for outdoor picks | Add NEA forecast when the date is ≤ 4 days away (FR-15) |
| Sign-in, digest, partner offers | Not built (P1/P2) | FR-14, FR-18–20 |

## PRD coverage

- **P0 (FR-01 to FR-12)**: implemented. FR-11 and FR-12 are browser-local as described above.
- **P1**: FR-13 RSVP (via messaging reply links), FR-15 rain backup (without NEA data) and FR-16 Surprise me are built. FR-14 sign-in and FR-17 content hub are not.
- **NFRs**: mobile-first at 360–430 px, 44 px tap targets, sticky thumb-reach CTAs, WCAG-minded contrast, labels and focus styles, light/dark themes, an installable PWA with an offline shell, no third-party trackers, and no images to slow LCP (category art is CSS gradients plus emoji).
